# Source-to-knowledge workflow

## Stage A — Capture
Put newly acquired books, papers and articles in the private Drive folder `00-Inbox`. Do not copy raw files into the Git repository. Register title, version, author(s), DOI/ISBN/URL, language and access rights.

## Stage B — Organize
- De-duplicate records and assign `BOOK-`, `PAPER-`, or `ART-` stable IDs.
- Relocate original attachments to private `01-Books`, `02-Papers`, or `03-Articles`.
- Preserve the original edition/version and the right to access it.
- Keep original files untouched when making extracted or processed derivatives.

## Stage C — Read and reason
Produce an original note with a transparent distinction:
1. **Source:** what the author actually asserts (with location when verified).
2. **Interpretation:** your analysis of what the claim means or implies.
3. **Transfer hypothesis:** whether a mechanism might be reused elsewhere.
4. **Question:** what would distinguish a good inference from a misleading analogy.

## Stage D — Transform into teaching
Connect concepts to a `MOVE-` card and micro/research exercises; specify prerequisites and transfer checks. Separate teacher/editor records from student-facing materials.

## Stage E — Publish
Check provenance, copyrights, access permissions, redacted URLs/IDs, scientific claims, readable English and link integrity. Sync authorized public notes to GitHub; keep the private catalog authoritative for raw file access.

## Status vocabulary
`inbox` → `catalogued` → `reading` → `annotated` → `verified`; a note's completion status is not the same as a source's content-verification status.

## Future scale
A file can move between local disk, Drive, Zotero or object storage without changing its stable source ID. The repository is the knowledge layer, not a general-purpose cloud drive.
